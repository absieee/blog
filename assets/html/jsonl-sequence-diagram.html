Field Reference

Identity Fields

uuid
Unique ID for this single JSONL entry. Every entry has one.
parentUuid
Points to the previous entry — forms the conversation chain. null on the first message.
promptId
Stable across all entries belonging to the same user-initiated prompt. Appears on user entries only. Links tool results back to the original turn.
sessionId
The top-level session (matches the folder name). Shared by all entries in a session.
agentId
Which subagent produced this. Matches the filename. Main thread has no agentId.
requestId
One HTTP request to the Anthropic API. Multiple JSONL entries share the same requestId when they are different content blocks (thinking / text / tool_use) streamed from one call.
message.id
The Anthropic API's own message ID (msg_…). Same as requestId grouping — all blocks from one API call share this.
attributionAgent
Which skill/agent config triggered this API call (e.g. "prep-hiring-manager").
sourceToolAssistantUUID
On tool_result entries: points to the assistant entry that made the tool_use call.

Token / Usage Fields

input_tokens
Tokens sent to the model that were not in the cache. Billed at the standard input rate (~$3/Mtok for Sonnet). In a long conversation this is usually tiny because most context is cached.
cache_creation_input_tokens
Tokens being written into the prompt cache for the first time this turn. Costs ~1.25× standard input (you pay a premium to store it). Worth it because future turns read it cheaply.
cache_read_input_tokens
Tokens read from the cache instead of re-sent. Costs ~0.1× standard input — 10× cheaper than fresh input. This is why caching is so valuable in long agentic runs.
cache_creation.ephemeral_5m_input_tokens
Subset of cache_creation going into the 5-minute TTL cache bucket. Used for short-lived context (tool results mid-turn). Cheaper to store than 1h.
cache_creation.ephemeral_1h_input_tokens
Subset going into the 1-hour TTL bucket. Used for longer-lived context like the system prompt or large files read early in a session.
output_tokens
Tokens the model generated. Billed at the output rate (~$15/Mtok for Sonnet — ~5× input). Kept small by streaming: intermediate "thinking" and "text" blocks often show output: 1 while streaming.

Content / Type Fields

type: "user"
Either a real human message (plain string content) or an injected tool result (content is array with tool_result object). Both use role: "user" in the Anthropic API.
type: "assistant"
One content block from Claude — thinking, text, or tool_use. One API call produces one or more of these entries.
content[].type: "thinking"
Extended thinking block. The actual thought is redacted in storage; a cryptographic signature is kept so Anthropic can verify integrity.
content[].type: "tool_use"
Claude calling a tool. Contains id (links to result), name (Bash / Read / WebSearch etc), input (args), caller.type (direct = Claude called it; harness = framework called it).
content[].type: "tool_result"
The tool's output, returned as a user-role message. tool_use_id links it back to the tool_use entry. is_error flags failures.
isSidechain: true
Every entry in this file has isSidechain: true — all 115.
This means the whole file is a detached branch of the conversation, not the main interactive thread. When Claude Code spawns a subagent (via the Agent tool), it opens a new JSONL file in the subagents/ directory and all its entries are tagged isSidechain: true.

The main thread (the file named by sessionId, one level up) has isSidechain: false. It contains the user's typed messages, Claude's top-level replies, and the Agent tool_use entry that kicked this subagent off. The subagent's work happens entirely in its own file, in parallel with anything else the main thread might be doing.

Practical implication: if you're parsing costs or debugging, you need to look in both places — the main session file and all files under subagents/. The token usage in this file is entirely separate from (and additive to) the main thread's usage.
stop_reason
null while streaming mid-turn. "tool_use" when Claude stopped to wait for a tool. "end_turn" on a final response. "max_tokens" if truncated.
Why are there 3 entries for one API call? Claude Code streams each content block (thinking → text → tool_use) and logs each as a separate JSONL entry in real-time. They share the same requestId and message.id — that's how you know they came from one HTTP request. The parentUuid chain links them sequentially. Early blocks in a streaming response show output: 1 — a placeholder. Read the final block in each request (where stop_reason ≠ null) for accurate totals.

Why does call #4 spike to 3,850 input_tokens? Call #3 ran 5 tools in parallel (WebSearch + WebFetch + 3 story file Reads). All 5 results landed simultaneously in the conversation as tool_result entries. When call #4 started, those 5 results were the most recent additions to the prompt — they hadn't been incorporated into a cache checkpoint yet. So they came in as fresh (uncached) input_tokens: 3,850.
The cache only extends to where the previous generation ended. Anything appended after that (tool results) is always fresh until the caching system creates a new checkpoint that includes them.

Why does call #5 recover to input_tokens: 1 despite also receiving 6 tool results? Call #5 writes a large cache_create: 9,342. This checkpoint captures the previously-uncached 3,850 tokens from call #3's results plus call #4's 6 new tool results in one go. Once checkpointed, those tokens are served from cache at 0.1× cost for every subsequent call. The spike was one-time; calls #6–22 all show input_tokens: 1.

The cache snowball. Call #1: cache_read 0. Call #10: cache_read 0 (anomalous reset, likely a Write boundary). Call #22: cache_read 65,186. By the end, 65k tokens — the entire conversation history, all files read, all web results — is served from cache on every single API call at 10× discount. This is why long agentic runs are cheaper than they look from the output count alone.
