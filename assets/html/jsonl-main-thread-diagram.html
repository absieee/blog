Entry Type Reference — Main Thread Only

New types (not in subagent files)

type: "last-prompt"
Written at session open. Records the uuid of the most recent visible message (leafUuid) so the harness can resume scrolling to the right point. Updated every turn. No uuid of its own — not part of the message chain.
type: "permission-mode"
Records the active permission mode (bypassPermissions / default / etc.) as a session-level snapshot. Written whenever it changes and at session open. The harness uses this to restore state on resume.
type: "ai-title"
Auto-generated session title, probably produced by a lightweight title-generation call after the first user prompt. Appears in the sessions list UI. Not part of the conversation chain.
type: "file-history-snapshot"
Snapshot of edited files before a user prompt is processed. Enables undo — the harness can restore file state if something goes wrong. messageId links it to the upcoming user entry.
type: "system" · subtype: "api_error"
Logged for every failed HTTP call to Anthropic. Contains full error details (status, headers, requestId). The harness retries up to maxRetries times with exponential backoff (retryInMs grows each attempt). After exhausting retries it generates a synthetic assistant message.
type: "system" · subtype: "turn_duration"
Emitted after every turn completes (real or error). Records wall-clock time (durationMs) and total messages in chain (messageCount). Used for performance tracking and displayed in the UI status line.
attachment · hook_success
Raw log of a hook execution — command, exitCode, durationMs, stdout, stderr. The stdout for a SessionStart hook contains JSON with hookSpecificOutput.additionalContext holding the skill text.
attachment · hook_additional_context
The harness extracts the additionalContext from hook_success.stdout and stores it here as a clean array. This is what actually gets injected into Claude's system prompt as a <system-reminder> block.
attachment · deferred_tools_delta
Incremental update to the available tool list. Tools are registered lazily — not all loaded at session start. Each delta adds/removes/readds tool names. pendingMcpServers lists MCP servers still initialising. Claude sees tool names but must call ToolSearch to get full schemas.
attachment · agent_listing_delta
Lists available named subagent types (claude, Explore, prep-hiring-manager, etc.) with one-line descriptions. Injected into Claude's context. These come from agent definition files, not SKILL.md.
attachment · skill_listing
Catalogue of all available skills — name + description from each skill's frontmatter. Injected as a <system-reminder>. Claude uses this to know which skills exist. Full skill content is only loaded when the Skill tool is invoked.
attachment · opened_file_in_ide
IDE extension context — which file is currently open. Claude receives this as implicit context without the user needing to mention it.

User entry content tags

<command-name>
Wraps the name of a slash command (e.g. /login, /model). Tells Claude and the harness this is a command invocation, not free text.
<command-message>
Human-readable label for the command (often same as command-name).
<command-args>
Arguments passed to the slash command (empty if none).
<local-command-caveat>
Wrapper injected before any slash-command sequence. Tells Claude: "Don't treat what follows as conversation input unless I ask you to." isMeta: true marks it as infrastructure.
<local-command-stdout>
Output of a slash command or local operation, stored as a user message. Claude ignores this per the caveat. The harness records it for completeness and for the conversation replay.

In the subagent file there was 1 promptId (the original delegation). In a main thread file, each user-initiated turn gets a new promptId. This includes:
• Every time the user types a message
• Every time the harness re-queues the same message after an error
• Slash commands that generate output (/model, /login)

The skill content pipeline: SKILL.md → hook → <EXTREMELY_IMPORTANT> → <system-reminder>
1. A skill is defined in a .md file with frontmatter. The body contains the instruction text including any tags the skill author puts there (like <EXTREMELY_IMPORTANT> — that's just markdown text inside the file).
2. A SessionStart hook runs at session open and calls a script that reads the using-superpowers skill and outputs it as JSON in stdout under hookSpecificOutput.additionalContext.
3. The harness logs the raw hook run as a hook_success attachment, then extracts the content and creates a hook_additional_context attachment.
4. That content is injected into Claude's actual API prompt as a <system-reminder> block — the tag wrapping is added by the harness, not by the skill file.
5. Claude reads it as system-level instruction before processing the user's message.

The skill_listing is separate from the hook content. The skill_listing attachment is a directory (names + one-liners). The hook content is the full text of one specific skill. Both end up in Claude's context but via different mechanisms.
